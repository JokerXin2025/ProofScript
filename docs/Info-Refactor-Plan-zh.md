# 统一 Info 系统重构实施计划

依据：[统一 Info 系统设计](Info-Architecture-zh.md)。本文将已确认的架构方向拆成可独立验收的阶段。以下任务均为待实施，本次交付为阶段规划。

## 执行原则

- 以当前工作区作为基线，保留已有修改；先区分既有问题和本次引入的问题。
- 每阶段明确产物和验收条件，优先形成较小、完整的变更集。
- 新核心、模型和命令先通过独立测试入口接入；阶段 5 完成之前，默认入口继续使用完整的旧链路。
- 新旧命令不能在同一入口重复注册。过渡模型使用明确命名空间；兼容别名与旧定义替换在切换时统一处理。
- 默认入口切换时，同时更新 Lean 命令、页面集成、导出、Python 消费端及默认配置。不能把新事件送进旧合并器。
- 配置核心所需的基础拆分提前做；大规模路径迁移与文件整理在端到端切换之后做。
- 每阶段运行与改动相关的检查；完成目录迁移后统一做最终完整回归。

## 阶段总览

| 阶段 | 目标 | 主要产物 | 依赖 |
| --- | --- | --- | --- |
| 0 | 明确基线与迁移契约 | 行为矩阵、依赖图、兼容边界 | 无 |
| 1 | 字段定义只有一个来源 | Codec、Schema、Derive、共享语法 | 0 |
| 2 | 更新与导入规则只有一套实现 | Patch、State、Resolve、来源诊断 | 1 |
| 3 | 六种命令使用统一框架 | 六种模型、领域约束、薄命令入口 | 2 |
| 4 | 页面、引用与配置时序一致 | 项目关联、页面快照、产物绑定 | 3 |
| 5 | 打通导出与 Python，正式切换 | 新协议、导出工具、Python 适配 | 4 |
| 6 | 完成目录重组与旧实现清理 | 新目录、公共入口、兼容导入 | 5 |
| 7 | 完成迁移验收与文档 | 回归结果、迁移指南、维护规范 | 6 |

阶段 0–2 完成通用核心；阶段 3–4 完成新系统的 Lean 集成；阶段 5 是正式切换点；阶段 6–7 完成结构整理和交付。

## 阶段 0：基线与迁移契约

目标：明确哪些行为保留、哪些行为有意改变，以及哪些当前失败属于既有问题。

任务：

- [ ] 清点六个命令的字段、语法、默认值、嵌套类型、目标解析、更新规则和消费位置。
- [ ] 梳理 Lean import 依赖与 Python 数据读取路径，标出字段白名单和重复合并逻辑。
- [ ] 记录当前可运行的 Lean、Python、示例站点检查及其结果；核对 Lake 测试 roots 与实际文件。
- [ ] 记录已有协议版本、字段形状和 `.ProofScript` 产物；将版本不一致等已有问题单独归因。
- [ ] 建立行为矩阵：保留行为、迁移变化、暂不处理的问题。迁移变化至少包含本地配置生效、重复配置、extra、ProjectId 和 page_end 快照。
- [ ] 固定协议版本策略、公共命名空间、临时测试入口，以及旧导入路径的兼容范围。
- [ ] 固定项目选择、首次归属、reset、集合合并、冲突消解、页面关闭后更新等语义。

验收：行为矩阵可以直接用于编写后续测试；相关基线可复现或有明确失败原因；没有依赖“默认取最后一个项目”等未说明的选择。

## 阶段 1：Schema、Codec 与派生机制

目标：验证统一框架最核心的可维护性收益——字段无需在多处重复列举。

主要位置：`Info/Value.lean`、`Codec.lean`、`Schema.lean`、`Derive.lean`、`Syntax.lean`，以及必要的 `Foundation/Source.lean`。

任务：

- [ ] 实现 ExtraValue、字段路径、结构化诊断与源码位置。
- [ ] 实现基础 codec：字符串、数字、布尔、Option、列表、对象、枚举；支持规范化编码和协议描述。
- [ ] 定义 FieldSpec / InfoSpec，明确字段类型、默认值、必填标记、合并策略、局部校验和记录校验接口。
- [ ] 实现从普通结构体派生字段、投影、setter、codec 关联、编解码与 JSON Schema 的最小可用生成器。
- [ ] 原型验证字段属性与 deriving 时序；特殊规则可通过生成的字段句柄配置 SchemaOverrides，避免重复写字段表。
- [ ] 实现共享字段语法，包含 extra、none 与 reset 的区别、重复键检查及拼写提示。
- [ ] 用小型独立模型验证嵌套字段、默认值、必填字段和有约束的新类型；对暂不支持的依赖型默认值给出清楚诊断。

验收：在样例结构体中增加一个普通字段后，通用解析与 JSON 输出自动支持它；无需修改通用分派函数或第二份白名单。已知字段非法值不会降级为 extra，同命令重复字段会定位报错。

此阶段先验证派生机制，不提前搬迁全部生产模型。

## 阶段 2：持久化更新与导入合并

目标：把重复配置、来源跟踪、跨模块覆盖与冲突诊断统一成一套可验证的算法。

主要位置：`Info/Patch.lean`、`State.lean`、`Resolve.lean`、`Elab.lean`、`Foundation/ModuleGraph.lean`。

任务：

- [ ] 定义可序列化的更新事件，记录 schema 身份/版本、目标、owner、序号、字段操作和来源。
- [ ] 实现初始化与上下文绑定记录，确保上下文默认值可以从 `.olean` 重建。
- [ ] 实现未赋值保留、set、none、reset、普通列表替换、按键合并与 extra 逐键更新。
- [ ] 实现“先解析整条命令，再一次性提交”的 elaborator 核心。
- [ ] 实现持久化环境扩展；缓存必须随环境和查询边界变化，避免编辑器重新 elaboration 后读取旧值。
- [ ] 实现显式接受模块与边界的 resolver；批处理环境中不能依赖 exporter 自身的 mainModule。
- [ ] 实现钻石导入去重、祖先覆盖、独立字段合并、冲突来源保留及本地 patch 消解。
- [ ] 实现强类型查询、消费依赖接口和完整性校验入口；允许尚未消费的配置暂时不完整。

验收：纯算法测试与真实多模块导入测试均通过；在不同 mainModule 的环境中能重建指定模块的视图；汇总模块可以解决独立导入冲突；跨 `.olean` 的初始化、extra、reset 与来源位置正确保留。

## 阶段 3：六种模型和命令迁入统一框架

目标：通过独立入口完整实现六种新命令，并使用真实配置验证框架。

主要位置：`Info/Project.lean`、`Theorem.lean`、`Script.lean`、`Definition.lean`、`Variable.lean`、`Phrase.lean`、`Command.lean`。

建议按三组推进；每组完成自己的领域测试后再扩展到下一组。

### 3A：Project / Theorem

- [ ] 实现 ProjectInfo、TheoremInfo 和稳定的 ProjectId。
- [ ] 实现显式项目选择、无目标简写和活动绑定歧义诊断。
- [ ] 持久化首次 theorem info 的项目归属；后续普通字段更新保持归属。
- [ ] 支持重复更新和 extra，统一声明名解析。

### 3B：Variable / Phrase / Definition

- [ ] 实现 VariableInfo、PhraseInfo、DefinitionInfo 及 style、arguments、kind 等嵌套模型。
- [ ] 将语言合并、styles 整体替换、参数范围、alias/unwrap 互斥等规则迁入 schema/领域校验。
- [ ] 定义 alias 依赖和环检查；明确动态后端查询的校验边界。
- [ ] 将现有基础 Lean2TeX 配置作为新框架的真实测试输入。

### 3C：Script

- [ ] 实现普通模板、策略模板、case、introducer、颜色和 renderer 的强类型模型。
- [ ] 拆出轻量脚本注册/契约查询，避免配置模型依赖完整执行与录制引擎。
- [ ] 迁移多语言模板、inline、分支、占位符及录制字段兼容性检查。
- [ ] 将现有基础脚本与 Mathlib 展示配置用于新入口验证；必要的执行/展示拆分在这里完成。

公共任务：

- [ ] 六个命令均变成目标解析加通用入口调用，取消字段字符串 if/else 链。
- [ ] 配置命令只写环境；新系统中移除逐条命令导出文件的副作用。
- [ ] 在隔离的集成入口中验证六个命令共同使用；避免旧、新 syntax/elab 重复注册。

验收：六种配置都能多次更新、接收 extra 并给出一致的诊断；现有配置样本的保留行为一致，有意改变的行为符合阶段 0 的矩阵。默认用户入口此时仍未切换。

## 阶段 4：页面、引用与配置快照集成

目标：解决配置更新后不同组件看到不同元数据的问题。

主要位置：`Page/Command.lean`、定理与引用组件、Info 快照状态、`Output/Manifest.lean`、脚本录制契约。

任务：

- [ ] 引用组件先保存声明身份，将展示信息解析统一放到 page_end。
- [ ] 标题、引用、ProjectId 对应项目内容、script/definition/variable/phrase 配置使用同一消费边界。
- [ ] 实现依赖集合收集：页面声明、规则、表达式常量及领域 dependencies；renderer 声明额外依赖。
- [ ] 实现冻结快照，生成包含规范化内容、schema 版本与录制契约版本的稳定摘要 ID。
- [ ] 让 page/proof 通过会话或产物清单绑定具体 snapshotId；不能仅查找模块最新配置。
- [ ] 记录实际录制契约版本，避免旧 proof 与后来更新的 recordedFields 混用。
- [ ] 持久化最小产物清单与快照；保留现有页面/proof/resource 内容生成方式。
- [ ] 明确并实现 page_end 后更新、无页面独立 proof、无 page_end 配置模块的处理路径。

验收：较晚的 info 更新能一致影响该页标题、引用和渲染；page_end 后更新不改变已冻结页面；仅更新外部定理 tags 不改变项目归属；未使用的不完整配置不阻塞无关页面。

本阶段的页面集成也通过新入口验证，避免旧 Python 消费尚未完成的新协议。

## 阶段 5：统一导出、Python 适配与正式切换

目标：形成第一条完整可用的新链路，再切换默认入口。

主要位置：`Output/Path.lean`、`Info.lean`、`Main.lean`，Lake facet，`PS4HTML` 与 `Lean2TeX` 配置消费端，生成的 JSON Schema。

任务：

- [ ] 统一模块路径编码、schemaVersion 和输出 envelope；生成可供后端消费的协议 schema。
- [ ] 实现独立 Lean 导出工具，从 `.olean` 读取模块事件、初始化/绑定、冻结快照与产物清单。
- [ ] 为无页面独立产物解析模块结束视图；无 page_end 配置模块正常导出事件。
- [ ] 接入现有 Lake 构建流程，明确页面资源生成与配置导出的先后关系。
- [ ] 实现 staging、完成版本清单与原子发布入口；覆盖空事件与删除产物，避免旧输出残留。
- [ ] Python 改为读取统一快照，并将强类型协议转换为现有渲染模型；保留 backend 所需的运行时检查。
- [ ] 项目展示与引用按 ProjectId 工作；移除“发现多个项目文件即报错”的旧限制。
- [ ] 删除或停用新协议路径上的 Python 导入合并器；未知版本给出明确迁移提示，不静默套用旧算法。
- [ ] 验证缓存模式从已完成快照直接构建，不运行 Lean。
- [ ] 更新默认配置与新入口所需的导入，在同一个完整变更中切换 `ProofScript.lean`、页面集成与 Python 默认读取路径。

正式切换门槛：代表性站点从干净输出目录构建成功；缓存构建成功；引用、模板、表达式排版与附加字段正确；编译/导出失败不会发布半套新配置。

此阶段的新链路验收通过前，继续通过独立入口推进。验收通过后旧系统停止承担生产配置合并，避免长期双轨维护。

## 阶段 6：文件结构整理与旧实现清理

目标：让物理目录与已建立的职责边界一致，完成大型文件调整。

任务：

- [ ] 将根 Data 中的领域信息分别归入 Info，将公共源码位置和模块图放入 Foundation。
- [ ] 从 Page/Component/Theorem 移除元数据命令、存储和协议代码。
- [ ] 清理旧 Render/Lean2TeX registry 的配置事件、合并和文件输出，保留需要的领域注册能力。
- [ ] 将通用路径与协议工具集中到 Output，消除底层配置对 Page 的依赖。
- [ ] 完成 Script/Config 的注册数据与语法实现拆分；只在有明确职责边界时继续拆分 Basic。
- [ ] 将内置展示配置集中到 Defaults；Mathlib 的 tactic 实现与展示配置分别组织。
- [ ] 调整公共聚合入口，检查模块依赖无循环；旧导入路径只保留计划中的薄转发。
- [ ] 删除临时入口、桥接代码和已失去用途的旧模型；处理公共类型名的兼容别名。
- [ ] 全局检索残留字段白名单、旧协议路径、重复合并和逐命令导出调用，逐项确认归属。

验收：新目录符合架构依赖方向；公开入口与计划保留的旧导入路径都可编译；一个领域字段的修改不会要求同步修改多份核心字段列表。

目录迁移尽量单独形成机械变更；必要的语义修复单独说明，便于审阅。

## 阶段 7：完整验收与维护交付

目标：确认新架构、构建与用户迁移均完成。

任务：

- [ ] 运行完整 Lean 检查、Python 配置/渲染测试和示例站点构建；关联阶段 0 的既有失败记录。
- [ ] 验证输入检查、重复更新、extra、reset、跨模块冲突与消解、项目归属和快照时序。
- [ ] 验证 `.olean` 配置重建、删除配置后的输出、隔离输出根、缓存构建和失败发布行为。
- [ ] 核对页面、proof、引用、表达式渲染与现有计算/资源组件的边界，避免目录调整破坏无关能力。
- [ ] 更新 README、JSON 协议文档、命令示例、构建说明与维护者开发指南。
- [ ] 编写迁移指南，明确本地配置生效、项目引用、附加字段形状、旧缓存重建和旧导入兼容范围。
- [ ] 记录兼容转发的后续移除条件；确认不存在默认仍生效的旧合并器。

验收：阶段 0 行为矩阵中的条目均有明确结果；有意改变的行为已文档化；普通字段和新 info 种类都有清楚的扩展步骤；完整构建及缓存路径通过验证。

## 可并行的工作与依赖

- 阶段 1 的 schema API 确定后，codec/derive 与纯 patch 数据设计可以并行；生产领域迁移仍等待通用核心通过验收。
- 阶段 3 的三组领域迁移可在目标解析和核心接口稳定后并行；Script 组的录制契约拆分是阶段 4 的前置条件。
- 阶段 4 的快照/manifest 协议确定后，Lean 导出工具与 Python 适配可以并行实现，使用相同的协议样本；正式切换等待两边联合验证。
- 大型路径迁移集中在阶段 6，避免多人同时移动同一文件。必要的基础抽取按前述阶段提前执行。

开始实施时从阶段 0 着手，再按验收条件推进。
